# 参赛方向选型记录

> 调研日期：2026-11-26 ｜ 面向：第四届大学生信息存储技术竞赛 · 自由赛道
> 结论：从零实现轻量向量存储引擎（候选 A，已采纳并定名为 **RAGStore**）

本文记录自由赛道的方向选型过程：团队可选的方向不止一个，选定其中一个之后，
其余方向为何不选，以及选定方向的完整事实清单。

## 〇、结论

**候选 A（RAGStore）已被采纳为参赛作品**，并按存储竞赛的叙事定名为
**RAGStore：面向检索增强生成的轻量级向量存储引擎**。

- Rust crate 与二进制名为 `ragstore`，环境变量前缀为 `RAGSTORE_`；
- 构建通过（10.75 s），143 项单元测试与 15 项协议测试全部通过，
  差分自测、公开用例集、召回率校验与语义校验脚本全部通过；
- 源码与文档已推送至 GitHub 仓库 `AndyCuihaoyi/ragstore`，服务器工作区为 `~/StorageContest`。

> **性能数字更正（2026-11-26）**：开发阶段的早期测量中出现过 1.51× 与 4.58× 两个倍数，
> 后续台账已判定这两者为口径产物——查询阶段在块设备计数下读数为 0 B，
> 1.51× 则是未绑核测量下的噪声读数。
> 最终文档采用的同协议交错复测结果为：精确查询 948.9 → 428.8 ms（2.21×）、
> 近似查询 2773.5 → 428.3 ms（6.48×）、查询物理 I/O 0 → 0 B、
> 写入 746.0 → 548.7 ms（1.36×）、建索引 73.0 → 32.1 ms（2.28×）、
> 峰值内存 14 800 → 13 744 KB，Recall@10 均为 1.0。
> 详见《作品设计文档》3.4 节与 `source/docs/perf/bench-2026-11-26-summary.json`。

## 一、三个候选方向

### 候选 A · RAGStore —— 自研轻量向量存储引擎

| 维度 | 事实 |
| --- | --- |
| 代码 | Rust **14 226 行**，33 个源文件（src 13 771 行 + 集成测试 455 行），**零外部 crate**（仅 std） |
| 交付体积 | 受管文件 **3.2 MB** |
| 构建 | `cargo build --release --offline --locked` **10.84 s** |
| 测试 | **143 单测 + 15 协议测试 = 158 全绿**（2026-11-26 本机复跑确认） |
| 公开判题器 | `protocol_check/run.py` 对真实镜像 **20/20 PASS** |
| 崩溃恢复 | 宿主 + 容器内各 **12 轮 SIGKILL**，恢复幂等全绿 |
| 差分自测 | 13/13，含 exact ≡ ann 逐字节一致 |
| 实现范围 | 列式存储 + WAL + 缓冲池 + 块扫描 + IVF 索引 + 精确/近似双模式 TopK + 显式事务 + 崩溃恢复 + JSON Lines 协议 |
| 材料 | README 9.5 KB · `docs/design.md` · `docs/perf/`（ledger/PLAN/PROFILE + 原始 json） · `tools/` 20+ 脚本 |
| 契合赛题 | **Storage4AI / AI4Storage**：向量存储是 RAG 与 Agent 的底座 |

**硬指标**（同协议交错复测，10k 行 × 128 维 × 1000 查询，绑核单核，5 轮中位数）：

| 指标 | 对照版本 | 本作品版本 | 倍数 |
| --- | ---: | ---: | ---: |
| 查询 T（精确） | 948.9 ms | 428.8 ms | 2.21× |
| 查询 T（近似） | 2773.5 ms | 428.3 ms | 6.48× |
| 查询 B（块设备） | 0 B | 0 B | 持平（常驻页缓存） |
| 查询 M（RSS） | 14 800 KB | 13 744 KB | 1.08× |
| 写入 T | 746.0 ms | 548.7 ms | 1.36× |
| 建索引 T | 73.0 ms | 32.1 ms | 2.28× |
| Recall@10 有过滤 / 无过滤 | 1.0 / 1.0 | 1.0 / 1.0 | 持平 |

> ⚠️ **口径纪律**：工作区早期流传的「查询 T 26.0× / I/O 807×」是对更早的一次
> 未绑核测量的对比，不是对官方参考值的对比（官方参考值从未公布）。
> 对外文档必须使用上表的对照版本口径并**写明对照版本**，否则性能声明不成立，
> 决赛答辩现场会被追问。

**优点**：原创性无可指摘（自研存储/查询/索引/事务核心，零现成引擎）；完成度可当场演示；
性能与正确性全部有可复现脚本；交付体积小，构建秒级，交付周期内最稳。
**缺点**：单机单进程场景，缺少分布式与硬件维度；「AI4Storage」的 AI 关联需要靠应用层叙事补足
（向量检索服务 RAG / Agent）。

### 候选 B · 在成熟数据库内核上做 AI 能力增强

| 维度 | 事实 |
| --- | --- |
| 载体 | 一个已有的数据库内核分支，源码树体积 **526 MB**（压缩后大概率逼近 500 MB 上限） |
| 亮点 | AI 列 = 模型驱动派生列的自动维护与版本演进，含事务一致性设计（按 rid 原子 claim/发布、迟到结果守卫丢弃、`no_partial_visibility`） |
| FTS 亮点 | 构建/分词/查询三链路 9 指标调优；**同一份代码分数在 30.01–50.000 间波动，根因定位到评测端采样与基线重测噪声** —— 这是很有分量的方法论创新 |
| 文档 | 实现日志 178 KB + 测试报告 69 KB（方差根因分析占三章） |

**优点**：分量重、与「存储内核/性能优化」贴合最紧；FTS 的方差归因可独立支撑「创新性说明」。
**缺点**：需重新编译整个内核（20 核，耗时以小时计）；压缩包体积逼近上限；
多个方向要拼成一条统一叙事；官方判题依赖 mock server，复现门槛高。**交付周期内风险最高。**

### 候选 C · 上下文工程（应用层）

本质是「上下文采集—组织—检索—压缩—注入」的应用层工程，
**与信息存储领域的强关联度最弱**，且实现分散。
**结论：不建议作为主作品。**

## 四、结论与建议

**选定候选 A（RAGStore）**，理由是它的**可交付性最强**：构建秒级、交付 3.2 MB、测试全绿、
证据链完整，且 100% 自研在「原创性」这一首要维度上没有任何解释成本。

**候选 B 的方差归因（同一份代码 30.01→50.000 的根因分析）** 是全场最有方法论价值的内容，
即使不作为主作品，其思路也已写入《作品设计文档》第三章的测量方法论 ——
它证明团队具备对「测量方法本身」做批判性分析的能力，这在决赛答辩里极有说服力。

**打包口径提示**：官方规则为「自由赛道仅可上传 10 次，以最后一次提交为准」，实质是
**一个作品包**。因此不宜把多个方向混装成一个 zip，会让设计文档的「方案设计」无法收束。
